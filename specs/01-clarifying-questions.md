# 规格决策记录（Specification Decision Record）

> 本文件记录图书管理系统在进入正式需求规格前的全部关键规格决策。
> 起草方式：Agent 提出澄清问题 → 人类回答 → Agent 整理为结论。
>
> 共 **71 条决策条目**（D-00 ~ D-61，含 9 条补充条目 a/b 后缀），按 14 个类别组织。
>
> **状态标记说明**：
> - 【确认】= 由人类明确拍板，可直接作为实现依据
> - 【默认】= 人类未表态，Agent 按行业常规做法填定，供审查时快速确认
> - 【推论】= 由已有决策逻辑推导得出，需人类复核推导是否正确
> - 【待定】= 尚未决定，需在后续阶段确定
>
> 本文件经人类审查通过后，其结论将写入 `specs/02-requirements.md`，并作为基线冻结。

## 一、参与者与权限

### D-00 参与者清单

**决策**：系统参与者定义如下。

| 参与者 | 类型 | 目标 | 与系统的交互 |
|---|---|---|---|
| **读者（Reader）** | 抽象参与者 | 查找并借阅图书 | 通过读者端查询、预约、查看本人状态 |
| **学生读者（StudentReader）** | 读者的子类型 | 同上 | 同上；借阅额度依具体学历类型而定 |
| ├ 专科生（COLLEGE） | 具体类型 | | 5 册 / 30 天 |
| ├ 本科生（UNDERGRADUATE） | 具体类型 | | 5 册 / 30 天 |
| ├ 研究生（GRADUATE） | 具体类型 | | 10 册 / 60 天 |
| └ 博士生（DOCTOR） | 具体类型 | | 15 册 / 90 天 |
| **教师读者（TeacherReader）** | 读者的子类型 | 同上 | 20 册 / 90 天 |
| **图书管理员（Librarian）** | 具体参与者 | 代理读者完成借还，管理流通业务 | 通过馆员端办理借书、还书、查询、收缴罚款 |
| **系统管理员（SystemAdmin）** | 具体参与者 | 维护系统基础数据与规则 | 通过管理端管理借阅证、账号、书目、规则 |

**继承关系**：`StudentReader` 与 `TeacherReader` 泛化自 `Reader`。

**状态**：【确认】

> 依据：实验一要求"识别参与者和用例"；实验概述 §8.1 定义的服务对象范围。

### D-01 认证方式

**决策**：采用**简化版 JWT 登录**。

- 认证方式：用户名 + 密码（bcrypt 哈希存储），登录成功后签发 JWT Token。
- 明确不做：邮箱验证、找回密码、第三方登录（微信/统一身份认证）、细粒度 RBAC。
- 角色通过 Token 中的 `role` 声明判定，角色枚举为 `READER` / `LIBRARIAN` / `ADMIN`。

**与实验文档的差异说明**：实验文档默认"第一阶段不实现复杂登录认证，接口通过 ID 表示操作人"。本项目选择实现简化版真实登录，属于**本组的主动范围扩展**，理由是为了让分层架构中的认证职责有真实落点。此项选择需在实验报告中说明。

**状态**：【确认】

### D-01a JWT 与凭证的具体参数

**决策**：

| 项 | 取值 |
|---|---|
| Token 有效期 | 24 小时 |
| Refresh Token | 不实现。过期后需重新登录 |
| 密码哈希算法 | bcrypt |
| 密码最短长度 | 6 位 |
| 密码最长长度 | 24 位 |
| 密码复杂度要求 | 无（不强制大小写/数字/符号组合） |
| 用户名字段 | 全局唯一，长度 3-32 位，仅允许字母、数字、下划线 |
| 登录失败提示 | 统一返回"用户名或密码错误"，不区分是哪个错（防用户名枚举） |
| 登出 | 由客户端丢弃 Token 实现，服务端不做 Token 黑名单 |

**状态**：【确认】

### D-01b 时间与时区处理

**决策**：**存储用 UTC，显示用北京时间。**

| 环节 | 处理方式 |
|---|---|
| 数据库存储 | 统一存储 UTC 时间戳（Unix timestamp 或带时区的 DATETIME） |
| 服务端内部计算 | 全部以 UTC 进行，不混用本地时间 |
| API 传输 | ISO 8601 格式并带时区标识，例如 `2026-09-19T06:44:25Z` |
| 前端显示 | 转换为北京时间（UTC+8）展示，例如 `2026-09-19 14:44:25` |
| 测试断言 | 基于 UTC 断言，避免因运行环境时区不同而失败 |

**说明**：时间戳本身不含时区信息，时区仅影响显示。采用 UTC 存储可保证跨环境一致性；前端转北京时间可保证用户看到的是本地时间。**严禁**在数据库中存储不带时区标识的本地时间字符串。

**状态**：【确认】

### D-02 角色与账号关系

**决策**：**一个自然人可拥有多个账号，但每个角色最多一个账号。**

- 一个自然人（以真实身份论）可以同时是读者和图书管理员，但需分别注册 `reader` 账号和 `librarian` 账号。
- 同一个自然人针对同一角色**不得**拥有多个账号（不允许开两个读者号）。
- 一个账号只具备一个角色，不可多角色挂载。

**状态**：【确认】

> **说明**：此决策来自 Q2「允许交叉但账号不同」与 Q4「一账号一角色」的合并裁定。

## 二、账号与借阅证

### D-06 借阅证号格式

**决策**：`CARD` + 4 位年份 + 6 位序号，例如 `CARD2026000001`。由系统生成，全局唯一。

**状态**：【确认】

---

### D-07 借阅证唯一性

**决策**：**一名读者最多拥有一张有效借阅证。**

- 已注销（`CANCELLED`）的旧证不计入此限制。
- 若读者已有有效证，再次办证应失败，返回 `CARD_ALREADY_EXISTS`。

**状态**：【确认】

---

### D-08 借阅证有效期

**决策**：**不设过期时间**，借阅证一经办理长期有效，直至被注销或挂失。

系统仍保留 `expired_at` 字段（可空），以便未来扩展；当前业务逻辑不校验它。

**状态**：【确认】

---

### D-09 借阅证状态

**决策**：支持 4 种状态。

| 状态 | 含义 |
|---|---|
| `ACTIVE` | 有效，可正常借书 |
| `SUSPENDED` | 挂失或暂停，不可借书，可恢复 |
| `CANCELLED` | 已注销，不可借书，不可恢复 |
| `EXPIRED` | 已过期（当前不使用，字段保留） |

**状态**：【确认】

---

### D-10 借阅证注销方式

**决策**：**软删除**——状态置为 `CANCELLED`，记录保留。

保留理由（用户原述）：
1. 延续前序借阅记录，保证历史可追溯；
2. 防止违规（有注销记录的读者再次办证时可被识别）；
3. 允许反悔（必要时可恢复）。

**状态**：【确认】

---

### D-11 账号与借阅资格的先后关系

**决策**：**先注册账号，再由系统管理员办理借阅证，办证后方具备借阅资格。**

- 仅注册账号而未办证的读者：可登录、可查询图书，**不可**预约图书，无借阅额度。
- 无有效借阅证时发起预约 → 返回 `CARD_REQUIRED`。

**状态**：【确认】

### D-13 借阅数量计算口径

**决策**：读者当前"占用额度" = **未归还的借阅记录数 + 有效预约数**。

用户要求（原述）："包含预约借书占位，且超时未归还的书要求包含在内。要求这个计算不要出错。"

明确计入：

| 项目 | 是否计入占用额度 |
|---|---|
| 已借出、未归还 | ✅ 计入 |
| 已借出、已超期且未归还 | ✅ 计入 |
| 有效预约（排队中） | ✅ 计入 |
| 已归还 | ❌ 不计入 |
| 已取消或已失效的预约 | ❌ 不计入 |

**判定公式**：
```
占用额度 = count(Loan where status IN (BORROWED, OVERDUE))
         + count(Reservation where status = ACTIVE)
占用额度 < 该读者类型的最大借阅数量  →  允许借书
```

**状态**：【确认】

> **风险提示**：此口径意味着"预约也占额度"。若某读者预约了大量图书，其可借数量会相应减少。这是用户明确要求的口径，测试需覆盖。

---

### D-14 借阅期限起算与到期判定

**决策**：**精确到时刻**。

- 起算：`borrowed_at`（借出瞬间的时间戳）。
- 到期：`due_at = borrowed_at + 借阅天数`。
- 判定：`returned_at > due_at` 即为逾期；`returned_at <= due_at` 视为按期。
- 到期日当天归还**不算超期**。

**状态**：【确认】

> 用户原表述："当天归还不算超额，借出时间戳算借出时间"——已统一为精确到时刻的比较，消除歧义。

---

### D-15 续借规则

**决策**：**允许续借，最多 2 次，每次续借延长 7 天。**

- 续借时长固定 7 天，**与读者类型无关**。
- 每次续借后，新的到期时间 = 原到期时间 + 7 天。
- 续借次数上限 2 次是针对**单条借阅记录**的；归还后重新借阅则计数重置。
- 预约**不影响**续借资格。
- 禁续条件：该借阅记录**已超期**，或读者**当前已超出最大借阅数量**。

**状态**：【确认】

> **说明**：用户原表述为"有预约的情况下，如果没有超期或者超额（最大额），就允许续借"。据此推导：是否存在预约不构成续借的禁止条件，真正的禁止条件是"超期"和"超额"。此推导需用户复核（见文末待复核事项）。
>
> **与实验文档的差异**：实验文档未提及续借功能，此为本组主动扩展。

## 四、借书流程

### D-16 借书校验项

**决策**：借书时必须依次校验以下 6 项，任一失败即拒绝。

| 序号 | 校验项 | 失败错误码 |
|---|---|---|
| 1 | 操作人具备图书管理员角色 | `PERMISSION_DENIED` |
| 2 | 借阅证存在且状态为 `ACTIVE` | `CARD_INVALID` |
| 3 | 未超出最大借阅数量（按 D-13 口径） | `BORROW_LIMIT_EXCEEDED` |
| 4 | 不存在超期未还的借阅记录 | `OVERDUE_LOAN_EXISTS` |
| 5 | 不存在未缴清的罚款 | `UNPAID_FINE_EXISTS` |
| 6 | 馆藏副本存在、属本馆、状态为 `AVAILABLE` | `ITEM_NOT_AVAILABLE` |

**状态**：【确认】

> 第 5 项依据 D-21（超期禁借 + 需缴清罚款）。

---

### D-17 重复借阅同一标题

**决策**：**允许**同一读者借阅同一图书标题的多个副本。

用户理由（原述）："允许，假设存在教师借书给其他学生阅览。"

**状态**：【确认】

---

### D-18 借书操作人记录

**决策**：**必须记录**。每条借阅记录保存办理该次借书的图书管理员 ID（`librarian_id`），用于追溯。

**状态**：【确认】

---

### D-19 借书前置确认步骤

**决策**：**需要**。借书为两步交互：

1. **查询步骤**：馆员输入借阅证号 → 系统校验并返回读者信息、当前借阅数量、剩余可借额度、是否存在超期或欠款。
2. **确认步骤**：馆员输入馆藏条码 → 系统完成借出。

用户定性（原述）："这个很必要，而且是固有逻辑。"

**API 体现**：拆为两个接口——`GET /api/circulation/borrow/precheck` 与 `POST /api/circulation/borrow`。

**状态**：【确认】

### D-26 罚款计算规则

**决策**：罚款按以下公式计算。

```
计罚天数 = 实际逾期天数 - 2（宽限期）
若 计罚天数 <= 0 → 罚款 = 0
罚款金额 = min(计罚天数 × 单价, 100)
```

- **宽限期 2 天**：逾期第 1、2 天不计罚。从第 3 天起计罚，且**只计超出宽限期的天数**（逾期 3 天 → 计罚 1 天）。
- **单笔封顶 100 元**：单条借阅记录产生的罚款不超过 100 元。

**示例**（中文图书，单价 0.20 元/天）：

| 逾期天数 | 计罚天数 | 罚款金额 |
|---:|---:|---:|
| 0 | 0 | 0.00 |
| 1 | 0 | 0.00（宽限期内） |
| 2 | 0 | 0.00（宽限期内） |
| 3 | 1 | 0.20 |
| 10 | 8 | 1.60 |
| 100 | 98 | 19.60 |
| 1000 | 998 | 100.00（触发封顶） |

**状态**：【确认】

> 宽限期与封顶由用户明确指定：用户原述"2 日宽限期，封顶 100 元（就当优化图书馆建设了）"，并选择"第 3 天起只计超出天数"与"单笔记录封顶"。

---

### D-27 罚款产生时机

**决策**：**还书时一次性计算并生成罚款记录**。

- 超期期间不预生成罚款记录。
- 还书时若判定逾期，则计算罚款并创建 `FineRecord`。
- 罚款记录初始状态为 `UNPAID`。

**状态**：【确认】

---

### D-28 罚款缴纳

**决策**：支持标记已缴纳。

- 可由**图书管理员**或**系统管理员**标记为 `PAID`。
- 缴纳方式为线下缴纳，系统仅记录状态，不接入支付。
- 未缴清罚款将导致借书被拒（见 D-21）。

**状态**：【确认】

---

## 七、预约规则

### D-29 可预约条件

**决策**：仅当**该图书标题下所有副本均不可借**时，才允许预约。

"不可借"包括副本状态为 `BORROWED`、`RESERVED`、`LOST`、`DAMAGED`、`REMOVED`。

若该标题下存在任一 `AVAILABLE` 副本 → 预约失败，返回 `ITEM_AVAILABLE_NO_RESERVATION`。

**状态**：【确认】

---

### D-30 预约排队机制

**决策**：按创建时间**先到先得**排队。

- 队列顺序由 `created_at` 升序决定。
- 读者可查询自己在队列中的位置。

**状态**：【确认】

---

### D-31 预约队列上限

**决策**：**每个图书标题最多 5 人排队**。队列已满时预约失败，返回 `RESERVATION_QUEUE_FULL`。

**状态**：【默认】

---

### D-32 预约自动预留

**决策**：**启用**。

还书时若该标题存在有效预约队列，副本状态置为 `RESERVED`，保留给队首读者。

**状态**：【确认】

---

### D-33 预约有效期

**决策**：

- 预约自创建起 **7 天内**有效；超期未借走则自动失效（状态置为 `EXPIRED`），队列顺延给下一位。
- 副本被预留后，队首读者应在 **7 天内**到馆借取，逾期未取则预约失效。

**状态**：【默认】

---

### D-34 预约取消

**决策**：**允许**读者主动取消本人预约（状态置为 `CANCELLED`）。

**状态**：【确认】

---

### D-35 重复预约限制

**决策**：同一读者对**同一图书标题**不得存在多个有效预约（状态为 `ACTIVE` 或 `READY`）。重复预约失败，返回 `DUPLICATE_RESERVATION`。

**状态**：【确认】

### D-46b 安全

**决策**：

| 项 | 要求 |
|---|---|
| 密码存储 | 必须使用 bcrypt 哈希，**严禁**明文或简单摘要（如 MD5） |
| 越权防护 | 所有写操作必须校验 Token 中的角色，不得仅依赖前端隐藏按钮 |
| 数据归属校验 | 读者只能访问本人数据，服务端必须校验资源归属，不得信任请求中的 reader_id |
| SQL 注入 | 全部通过 ORM 参数化查询，禁止拼接 SQL |
| 敏感信息返回 | 接口响应不得包含密码哈希 |
| 传输 | 演示环境使用 HTTP，不做 TLS（实验环境限制） |

**状态**：【确认】

---

### D-46c 可靠性、一致性与事务边界

**决策**：以下操作**必须**在单个数据库事务内完成，任一步失败则全部回滚。

| 操作 | 事务范围 | 失败后果（若不使用事务） |
|---|---|---|
| 办理借书 | 校验额度 → 创建 Loan → 更新 LibraryItem 状态 → 更新额度占用 | 并发下可能超额借出 |
| 办理还书 | 更新 Loan 状态 → 更新 LibraryItem 状态 → 生成 FineRecord（如超期）→ 处理预约预留 | 可能出现"已还但罚款丢失"或"副本状态错乱" |
| 预约图书 | 校验队列 → 创建 Reservation → 更新排队序号 | 队列顺序错乱或超员 |
| 办理借阅证 | 校验读者 → 生成证号 → 创建 BorrowCard | 可能出现同一读者两张有效证 |
| 续借 | 校验续借次数 → 更新 due_at → 递增续借次数 | 可能超出续借上限 |

**并发控制策略**：SQLite 采用文件级锁，配合应用层的数据库事务（`BEGIN IMMEDIATE`）保证串行写入。本项目**不实现**乐观锁版本号机制。

**状态**：【默认】

> 此项为实验一"架构设计须说明事务边界"的要求，01 文档原缺。

---

### D-46d 可用性与错误处理

**决策**：

- 所有业务规则失败必须返回明确、可读的中文错误提示，不得返回 500 或空白错误。
- 错误提示不得暴露内部实现细节（如堆栈、SQL 语句）。
- 前端在收到 401 时应自动跳转登录页；收到 403 时提示"权限不足"。

**状态**：【默认】

---

### D-46e 可维护性

**决策**：

- 严格遵循分层架构，禁止跨层调用（Controller 不得直接访问 Repository）。
- 业务规则集中在领域层与应用服务层，不得写在路由处理函数中。
- 代码需通过 `ruff` 或 `flake8` 静态检查（作为可选项，不作为交付硬性要求）。
- 所有公开函数需有文档字符串。

**状态**：【默认】

---

### D-46f 数据保留

**决策**：

- 借阅记录、罚款记录**永久保留**，不自动清理。
- 已删除（软删除）的图书与证书记录永久保留，仅对系统管理员可见。

**状态**：【确认】

> 依据 D-10、D-40 的软删除要求。

## 十、数据与持久化

### D-47 数据库选型

**决策**：SQLite 单文件数据库。**不提供** MySQL 切换支持（保持简单）。

**状态**：【确认】

---

### D-47a 借阅规则与罚款规则的可配置性

**决策**：**规则存数据库，可由系统管理员在线维护。**

设计要点：

- 借阅规则表 `borrow_policies`：按读者类型存储最大借阅数量、借阅期限。
- 罚款规则表 `fine_rules`：按借出物类型存储日罚款单价，并存储宽限期天数与单笔封顶金额。
- 系统管理员可通过 API 修改上述规则，修改即时生效（影响力仅作用于变更后的新操作，不追溯已产生的借阅记录）。
- 规则表在系统初始化时写入 D-12、D-25、D-26 定义的默认值。
- 代码**不得**将规则数值硬编码为常量，必须从规则表读取。

**理由**：实验一与实验二均要求实现"维护借阅规则和罚款规则"用例（UC-209），若规则写死在代码中，该用例将无法真实实现。

**风险提示**：规则可在线修改意味着借阅期限可能在借阅期间被改动。**决策：借阅记录在创建时快照当时的期限（`due_at` 已固定），规则变更不影响已存在的借阅记录。**

**状态**：【确认】

**状态**：【默认】

### D-49 领域继承的数据库映射策略

**决策**：**单表继承（Single Table Inheritance）**。

- `readers` 表包含 `reader_type` 字段区分 `COLLEGE` / `UNDERGRADUATE` / `GRADUATE` / `DOCTOR` / `TEACHER`。
- 领域模型中保留 `Reader` ← `StudentReader` / `TeacherReader` 的继承结构（用于 UML 表达与借阅策略分发），但数据库不拆表。

**状态**：【确认】

> 人类对继承体系未表态，交由 Agent 决定。选择理由：实验一明确要求领域模型体现继承关系，同时单表映射避免了多表 join 的实现成本。
