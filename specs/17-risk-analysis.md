# 风险分析（Risk Analysis）

> **文档编号**：`specs/17-risk-analysis.md`
> **制定依据**：当前全部 specs（`00` ~ `08`、`13`、`constitution`、`19`）
> **版本**：v1.0
> **日期**：2026-09-19
>
> 本文件识别本项目在规格与实现层面可能出问题的地方，给出**影响**、**可能性**、**缓解措施**与**责任归属**。
>
> **编写原则**：本文件的价值在于**诚实**。因此它包含本项目在设计过程中**主动接受的简化取舍**——那些不是失误、但确实构成风险的决定。回避这些等于放弃风险分析的意义。

---

## 1. 风险评级标准

| 等级 | 影响 | 可能性 |
|:---:|---|---|
| **高** | 导致功能不可用、数据错误、验收不通过 | 很可能发生或已存在 |
| **中** | 导致返工、性能下降、可维护性变差 | 有可能发生 |
| **低** | 影响有限，有明确绕过方案 | 发生概率低 |

**风险编号规则**：`R-<类别代号>-<序号>`

| 类别代号 | 含义 |
|:---:|---|
| `REQ` | 需求风险 |
| `MOD` | 建模风险 |
| `ARC` | 架构风险 |
| `DB` | 数据库风险 |
| `SEC` | 权限与安全风险 |
| `AI` | Agent 使用风险 |

**责任归属**：`Agent`（规格起草方）/ `人类`（审查拍板方）/ `共同`

## 2. 需求风险（REQ）

### R-REQ-01 需求被 Agent 编造（**高风险**）

| 项 | 内容 |
|---|---|
| **风险** | Agent 生成的需求规格（`02-requirements.md` 29 条 FR、50 条 BR）中，可能存在**并非来自用户或实验文档**的条目。例如"续借"、"到期提醒"、"馆藏统计"等功能均为 Agent 主动扩展。 |
| **影响** | **高**——若编造的需求与实际意图不符，后续全部设计与实现都建立在错误前提上。 |
| **可能性** | **高**——本项目 FR 数量 29 条，**超出实验文档要求的 16 条**，扩展比例接近一倍。这是客观事实。 |
| **当前状态** | 已通过 4 轮交互问答确认 14 项决策，用户对扩展表示认可（"续借体现策略模式 + 真实图书馆普遍支持"）。但**不等于逐条确认过全部 29 条 FR**。 |
| **缓解措施** | ① 人工审查阶段**逐条过 FR**，标注"实验文档要求"与"Agent 扩展"两类来源；② 对 Agent 扩展项，确认是否愿意保留；③ 若不愿承担，实验一只需删除对应 FR/BR/用例即可，成本可控（尚未写代码）。 |
| **责任** | 共同 |

### R-REQ-02 需求与实验要求存在隐性偏差（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | 实验文档明确点名的功能可能被 Agent 的扩展**稀释或覆盖**。例如实验要求"重点详细描述 5 个用例"，Agent 实际详述了 UC-101/102/102a/005/201 五个，但是否与实验文档点名的完全一致需核对。 |
| **影响** | 中——可能被扣分。 |
| **可能性** | 中。 |
| **缓解措施** | 已在 `04-use-case-model.md` §11、`05-domain-model.md` §11、`06-domain-class-diagram.md` §11、`08-package-diagram.md` §10 各附"与实验文档要求对照表"，逐项验证。审查时**只需核对这 4 张表**即可定位偏差。 |
| **责任** | 人类 |

### R-REQ-03 5 项待确认问题未裁定（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | `02-requirements.md` §7 留有 Q-01 ~ Q-05 五项待确认问题。**baseline 冻结后修改规格需走单独的修订流程**（宪法第四条），成本高于现在处理。 |
| **影响** | 中——冻结后发现问题需额外修订提交。 |
| **可能性** | 中（其中 Q-01、Q-03 已给出暂定方案并写入设计，风险较低）。 |
| **缓解措施** | **在打 `experiment1-specs-baseline-v1` 标签之前完成裁定**（见 `18-review-checklist.md` 的冻结前检查项）。 |
| **责任** | 人类 |

### R-REQ-04 非功能需求缺乏验证手段（**低风险**）

| 项 | 内容 |
|---|---|
| **风险** | 14 条 NFR 中，性能指标（查询 < 500ms、写操作 < 1s、50 并发）在实验一中**无从验证**，也没有专门的性能测试计划。 |
| **影响** | 低——决策 D-46a 已明确"性能非考核重点，指标仅作为设计约束"。 |
| **可能性** | 低。 |
| **缓解措施** | 已由 D-46a 显式降级为"设计约束而非验收指标"；索引设计（`13-database-design.md` §5）作为对应措施。 |
| **责任** | Agent（已标注） |

## 3. 建模风险（MOD）

### R-MOD-01 领域模型被实现细节污染（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | 实验文档明确要求审查"是否过早引入 Controller、Repository、DTO 到领域类图"。若 `05-domain-model.md` 或 `06-domain-class-diagram.md` 混入设计类，即违反此要求。 |
| **影响** | 中——直接对应实验审查项第 5 条。 |
| **可能性** | **低**——`05-domain-model.md` 开头即声明"本文件不包含任何设计类"，`06-domain-class-diagram.md` 同样声明范围界定，且两份文档的自查表均逐项验证。 |
| **缓解措施** | 审查时**grep 检查**：在 `05`、`06` 中搜索 `Controller`、`Repository`、`DTO`、`Mapper`、`Service Layer`，确认无命中（或仅出现于"不含"这类否定语境）。 |
| **责任** | 人类（可机械验证） |

### R-MOD-02 题录/副本两分模型的理解成本（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | `BookTitle`（题录）与 `LibraryItem`（物理副本）的分离是本系统的核心建模决策（`05-domain-model.md` §4.1）。若实现者（实验二的自己）理解偏差，可能导致预约记错对象、罚款算错类型。 |
| **影响** | 高（若实现错误）——预约针对标题、借出针对副本，搞错会导致预约逻辑失效。 |
| **可能性** | 中——这是最容易在实现时搞混的地方。 |
| **缓解措施** | ① `05-domain-model.md` §4.1 已用表格列出"5 个场景分别操作哪个对象"；② `06-domain-class-diagram.md` §10.1 专门论证为何要分离；③ 实现时对 `Reservation.title_id` 与 `Loan.item_id` 的区分设为首要检查项。 |
| **责任** | 共同 |

### R-MOD-03 领域层内部循环依赖（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | 若 `entities` 直接调用 `domain_services`（如 `Reader.can_borrow()` 内部 new 一个 `BorrowEligibilityService`），会形成 `entities → domain_services → entities` 循环。 |
| **影响** | 中——领域层内部成环，破坏可测试性。 |
| **可能性** | 中——这是 DDD 实现中的常见错误。 |
| **缓解措施** | `08-package-diagram.md` §5 已定义规则 **D-7** 明确禁止，并给出正确做法（由应用层协调）。审查时可 grep `domain/entities/` 中的 `domain_services` 导入。 |
| **责任** | 共同 |

### R-MOD-04 `OVERDUE` 派生状态被误持久化（**低风险**）

| 项 | 内容 |
|---|---|
| **风险** | `LoanStatus.OVERDUE` 在领域层保留但**不应持久化**（`05-domain-model.md` §5.1）。实现者可能误建三态 `status` 字段。 |
| **影响** | 中（若发生）——产生数据陈旧风险：记录超期后无人负责改状态。 |
| **可能性** | 低——已在 3 处标注（`05` §5.1、§5.3；`06` §5）并在 `13-database-design.md` §4.7 用 CHECK 约束固化为两态。 |
| **缓解措施** | `loans.status` 的 `CHECK (status IN ('BORROWED','RETURNED'))` 从数据库层拒绝三态写入。 |
| **责任** | Agent（已固化） |

## 4. 架构风险（ARC）

### R-ARC-01 业务逻辑回流到 Router（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | 实验二实现时，可能图省事把业务规则写进 FastAPI 路由函数（宪法第六条明令禁止）。 |
| **影响** | 高（若发生）——违反宪法，且业务规则无法被其他入口复用。 |
| **可能性** | 中——FastAPI 的 `Depends` 让"顺手查一下数据库"变得很容易。 |
| **缓解措施** | ① `07-architecture.md` §3.3 给出违规与正确的代码对照；② 定义可量化的判断标准：**Router 函数典型 1-3 行，超过 10 行即需审查**；③ 审查时 grep `presentation/` 中的 `db.query`、`select(`。 |
| **责任** | 共同 |

### R-ARC-02 领域层引入框架依赖（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | 实现时为省事给领域实体直接加 SQLAlchemy 映射（Active Record），导致领域层 `import sqlalchemy`。 |
| **影响** | 高（若发生）——违反宪法第五条，且领域逻辑无法脱离数据库单测。 |
| **可能性** | 中——Active Record 是"更省事"的写法，诱惑真实存在。 |
| **缓解措施** | ① ADR-05 已明确采用"ORM 模型与领域实体分离 + Mapper"；② 提供**机械检验方法**：删除 `fastapi`/`sqlalchemy` 后 `domain/` 应仍能导入并跑通单测；③ 审查时 grep `domain/` 中的框架导入。 |
| **责任** | 共同 |

### R-ARC-03 `CirculationService` 膨胀为"上帝服务"（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | `CirculationService` 依赖全部 7 个 Repository（`08-package-diagram.md` §4 已量化）。若编排逻辑持续堆积，会演变成难以维护的巨型服务。 |
| **影响** | 中——可维护性下降，测试困难。 |
| **可能性** | **中偏高**——借还书是本系统最复杂的操作，天然倾向于堆积。 |
| **缓解措施** | ① 已设定**审查阈值**：单个方法超过 50 行即需拆分；② 缓解方向明确——把判定逻辑全部下沉到领域服务（`BorrowEligibilityService`/`RenewalService`/`ReservationQueueService`），使 `CirculationService` 只剩"取数据 → 调领域 → 落库"骨架；③ 若仍膨胀，拆为 `BorrowWorkflow` 与 `ReturnWorkflow`。 |
| **责任** | 共同 |

### R-ARC-04 Mapper 层维护成本（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | ADR-05 要求 7 组 Mapper 做 ORM ↔ 领域对象双向转换。新增字段时需**同步改三处**（领域实体、ORM 模型、Mapper），漏改会导致数据静默丢失。 |
| **影响** | 中——字段遗漏不会报错，只会表现为"某个字段莫名是默认值"。 |
| **可能性** | 中高——手写 Mapper 的固有风险。 |
| **缓解措施** | ① 单元测试**必须覆盖 Mapper 往返转换**（`to_domain(to_model(x)) == x`），这是唯一能自动发现漏字段的手段；② 在 `15-test-plan.md`（实验二）中列为必测项。 |
| **责任** | 共同 |

### R-ARC-05 架构过度设计的嫌疑（**低风险**）

| 项 | 内容 |
|---|---|
| **风险** | 四层架构 + 6 种设计模式 + Mapper 层 + Repository 接口，对一个课程实验可能显得过重。可能被质疑"为模式而模式"。 |
| **影响** | 低至中——影响评分中的"设计合理性"判断。 |
| **可能性** | 中——审视者的合理质疑。 |
| **缓解措施** | ① 每处模式使用都有明确的问题指向（`07-architecture.md` §4 表格的"解决的问题"列）；② 8 条 ADR **主动拒绝了 3 项**被认为不必要的设计（乐观锁、审计表、PostgreSQL），可证明并非无差别堆砌；③ Mapper 层已论证为宪法约束的**必然产物**而非选择（ADR-05）。 |
| **责任** | 人类（需在答辩时能解释） |

## 5. 数据库风险（DB）

### R-DB-01 SQLite 无行级锁，并发受限（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | SQLite 的写操作全局串行化，无法支持高并发写入。 |
| **影响** | 中——若演示时多人同时操作，可能遇到 `database is locked`。 |
| **可能性** | **低**——本项目为课程演示规模，无并发压力。 |
| **缓解措施** | ① ADR-06 已明确接受此代价；② 通过 Repository 接口隔离，迁移 PostgreSQL 只需替换实现层；③ 若演示需要，可启用 SQLite 的 WAL 模式提升并发读能力。 |
| **责任** | Agent（已接受） |

### R-DB-02 无乐观锁，并发更新可能丢失（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | ADR-03 决定**不引入** `version` 字段与乐观锁。两个并发请求读同一副本、同时判断"可借"、各自写入，可能导致副本被重复借出。 |
| **影响** | 高（若发生）——一本副本对应两条 `BORROWED` 记录，数据不一致。 |
| **可能性** | **低**——SQLite 写串行化 + 事务原子性提供了兜底；且借书为图书管理员手工操作，实际并发概率极低。 |
| **缓解措施** | ① 副本借出改为**条件更新**：`UPDATE library_items SET status='BORROWED' WHERE item_id=? AND status='AVAILABLE'`，检查影响行数是否为 1，为 0 则拒绝；② 该写法不依赖乐观锁即可防重复借出；③ 已记录扩展位，迁移 PostgreSQL 时补 `version` 字段。 |
| **责任** | 共同（实现时须落实条件更新） |

### R-DB-03 证号生成存在并发撞号窗口（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | `card_no` 序号用 `MAX(SUBSTR(...)) + 1` 生成（`13-database-design.md` §4.4），两个并发办证请求可能算出同一序号。 |
| **影响** | 中——后者因 UNIQUE 约束失败，需重试。 |
| **可能性** | **低**——办证为管理员手工低频操作。 |
| **缓解措施** | ① `uq_borrow_cards_card_no` 唯一约束兜底，**不会写入脏数据**，只会拒绝；② 实现时对"取序号 + 插入"包在同一事务内；③ 若需彻底解决，可改用独立序列表 + `UPDATE ... RETURNING`，但当前规模不值得。 |
| **责任** | 共同 |

### R-DB-04 金额存 TEXT 导致 SQL 层无法数值校验（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | 为解决 SQLite 的 Decimal 精度问题，金额字段以 TEXT 存储（`13-database-design.md` §1.3）。**代价**：数据库层无法做数值比较与校验——`'10.00' < '2.00'` 按字典序成立。 |
| **影响** | 中——若应用层校验缺失，可能写入负单价或超范围封顶。 |
| **可能性** | 低——所有金额写入路径均经领域层 `Money` 值对象，其不变量已约束非负与两位小数。 |
| **缓解措施** | ① `Money` 值对象在构造与运算中强制 `quantize(0.01)` 与非负校验（`05-domain-model.md` §7.2）；② `PolicyService` 对规则更新做显式校验（BR-028 要求非负）；③ 单元测试覆盖边界值。 |
| **责任** | 共同 |

### R-DB-05 软删除与唯一约束的语义复杂化（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | 本项目对唯一约束采用了**两种不同策略**（`13-database-design.md` §4.5）：`username` 全局唯一（软删除不释放），`isbn` 部分唯一（仅活跃记录）。理解成本高，实现时易混淆。 |
| **影响** | 中——若搞反，会出现"用户无法重新注册"或"ISBN 重复录入"两类相反问题。 |
| **可能性** | 中。 |
| **缓解措施** | ① 已在文档中给出**语义区分表**（身份标识 vs 出版物标识）；② 3 处部分唯一索引集中列在 §5.1，便于对照实现；③ 测试须覆盖两种场景（软删除后同名用户名被拒 / 软删除后同 ISBN 被接受）。 |
| **责任** | 共同 |

### R-DB-06 `fine_records.operator_id` 失去引用完整性（**低风险**）

| 项 | 内容 |
|---|---|
| **风险** | 因收缴人可能是图书管理员或管理员（分属两表），`operator_id` 采用"单列 + `operator_role` 标识"且**不建外键**（`13-database-design.md` §4.9）。可能存入不存在的 ID。 |
| **影响** | 低——该字段仅用于留痕与展示，不参与业务判定。 |
| **可能性** | 低——该值由应用层从 JWT token 取当前登录人写入，无用户可控入口。 |
| **缓解措施** | ① `CHECK (operator_role IN ('LIBRARIAN','ADMIN'))` 约束角色合法；② 值来源不可伪造；③ 若需强引用完整，可改为双列方案（文档已列出备选）。 |
| **责任** | Agent（已说明） |

### R-DB-07 无全文索引，题名检索效率受限（**低风险**）

| 项 | 内容 |
|---|---|
| **风险** | `00-project-brief.md` §9 将"复杂全文检索"列为暂不实现，故题名检索用 `LIKE '%关键字%'`，无法走索引。 |
| **影响** | 低——本项目数据量为百级，全表扫描耗时可忽略。 |
| **可能性** | 低。 |
| **缓解措施** | ① 已在 `13-database-design.md` §5.2 显式标注此限制；② 若数据量增长，可启用 SQLite 的 FTS5 扩展。 |
| **责任** | Agent（已标注） |

## 6. 权限与安全风险（SEC）

### R-SEC-01 读者越权访问他人数据（**高风险**）

| 项 | 内容 |
|---|---|
| **风险** | 若接口设计为 `GET /readers/{reader_id}/loans` 并直接信任路径参数，任何登录读者都能通过改 ID 查看他人借阅记录。 |
| **影响** | 高——隐私泄露，且直接违反 BR-039 与宪法第七条。 |
| **可能性** | 中——这是最常见的 API 设计错误。 |
| **缓解措施** | ① `07-architecture.md` §6.1 明确要求改为 `GET /me/loans`，`reader_id` **必须从 JWT token 的 `sub` 取**，不得信任请求参数；② 文档给出反例与正例对照；③ 测试计划须包含"读者查他人数据返回 403"用例（宪法第十条测试清单已列）。 |
| **责任** | 共同 |

### R-SEC-02 权限校验遗漏或仅在表现层实现（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | 某接口忘记加 `require_role` 守卫，或校验只在前端做（隐藏按钮），导致直接调 API 即可越权。 |
| **影响** | 高（若发生）。 |
| **可能性** | 中——接口数量多（29 条 FR 对应的端点），逐个检查易疏漏。 |
| **缓解措施** | ① 权限矩阵（`07-architecture.md` §6.1，源自 D-05）逐功能域列出三角色权限，作为检查对照表；② 用**依赖注入守卫**统一实现，避免每个路由手写判断；③ 测试须覆盖"读者执行管理员操作失败"、"图书管理员执行管理员操作失败"两类（宪法第十条已列）。 |
| **责任** | 共同 |

### R-SEC-03 软删除记录对非管理员泄露（**中风险**）

| 项 | 内容 |
|---|---|
| **风险** | BR-037 要求已软删除的记录仅系统管理员可见。若查询接口未统一过滤，读者/图书管理员仍能查到已下架的图书或已注销的借阅证。 |
| **影响** | 中——违反业务规则，且是审查项"数据保留策略"的直接检查点。 |
| **可能性** | 中——过滤逻辑需在每个查询路径重复实现，易遗漏。 |
| **缓解措施** | ① 在 Repository 层统一实现"默认过滤软删除"的查询方法，管理员查询走独立的 `include_deleted=True` 变体；② 测试须覆盖"已删除记录读者不可见 / 系统管理员可见"（宪法第十条已列）。 |
| **责任** | 共同 |

### R-SEC-04 JWT 简化方案的安全边界（**低风险**）

| 项 | 内容 |
|---|---|
| **风险** | 决策 D-01a 采用简化 JWT：24 小时有效期、**无 refresh token**、无吊销机制。token 泄露后 24 小时内无法作废。 |
| **影响** | 低——本项目为课程实验，且 `00-project-brief.md` §9 已将"生产级安全加固"列为暂不实现。 |
| **可能性** | 低。 |
| **缓解措施** | ① 已由 D-01a 与 brief §9 明确界定范围；② 密码仍用 bcrypt 哈希（BR-045），不存明文；③ 禁忌事项已明确：日志中严禁记录明文密码与完整 token（`07-architecture.md` §6.4）。 |
| **责任** | Agent（已标注） |

### R-SEC-05 系统管理员初始化脚本的凭据管理（**低风险**）

| 项 | 内容 |
|---|---|
| **风险** | 首个系统管理员只能由初始化脚本创建（D-04），若脚本中硬编码密码，会随 Git 提交泄露。 |
| **影响** | 中（若发生）——凭据入库。 |
| **可能性** | 低——但这是常见疏漏。 |
| **缓解措施** | ① 密码必须通过**脚本参数或环境变量**传入，**严禁**硬编码；② `.env` 必须列入 `.gitignore`；③ 审查时 grep `init_db.py` 确认无明文密码常量。 |
| **责任** | 共同 |
