# 图书管理系统开发宪法（Constitution）

> **本文件是项目的最高约束，优先于任何个人偏好与 Agent 的自主判断。**
> 凡本文件与 `specs/` 下其他文档冲突，以本文件为准。
> 凡 Codex / Claude Code / CodeBuddy 等编码 Agent 的行为与本文件冲突，以本文件为准。
>
> 制定依据：`specs/00-project-brief.md`、`specs/01-clarifying-questions.md`
> 生效范围：本项目全部规格文档、UML 模型、源代码、测试与提交记录。

---

## 第一条 Specs 优先原则

**任何代码实现前，必须先完成对应的规格文档。**

- 规格文档集包括：需求规格、用例文本、用例图、领域模型、领域类图、架构设计、包图、数据库设计、详细设计、顺序图、API 规范、测试计划、任务拆解。
- 未完成上述文档前，Agent 不得创建任何业务代码文件。
- 若发现规格缺失或矛盾，应先修订规格，再实现代码；不得在代码中"顺手补上"缺失的设计。

**违反示例**：Agent 在 `03-use-cases.md` 尚未描述"归还流程"的情况下，直接实现 `return_book()` 服务方法。

## 第二条 Agent 起草，人类确认原则

**Agent 可以生成规格与代码初稿，但所有产出必须经人类审查后方可作为后续工作的依据。**

- Agent 每次修改文件前，须先输出实现计划，说明将要修改哪些文件、为什么。
- 人类确认计划后，Agent 方可执行修改。
- Agent 不得连续执行多个未审查的任务。
- 人类审查不通过时，Agent 须按反馈修订，不得争辩或跳过。

## 第五条 分层架构原则

**系统必须采用分层架构，至少包含以下四层。**

| 层次 | 职责 | 允许依赖 |
|---|---|---|
| **表现层 Presentation** | 接收 HTTP 请求、参数校验、返回响应 | 应用服务层 |
| **应用服务层 Application** | 组织用例流程、控制事务边界、权限校验 | 领域层、基础设施层接口 |
| **领域层 Domain** | 业务规则、实体、值对象、领域服务、策略 | 无（不依赖其他层） |
| **基础设施层 Infrastructure** | 数据库访问、ORM 映射、外部服务、JWT 实现 | 领域层接口实现 |

**依赖规则**：

- 依赖方向**单向向下**：表现层 → 应用服务层 → 领域层。
- 领域层**不得**依赖任何其他层，不得引用 FastAPI、SQLAlchemy 等框架。
- 基础设施层通过**实现领域层定义的接口**（Repository 接口）反向提供能力。

**违反示例**：在领域实体中 `import sqlalchemy`；在应用服务中直接读取环境变量。

## 第六条 MVC 分离原则

**Web 层应遵循 MVC 或类似分离思想，业务规则不得写入 Controller。**

- 在本项目（FastAPI）中，**router 函数即 Controller**。
- Router 函数**只允许**做四件事：接收请求、调用应用服务、捕获异常、返回响应。
- Router 函数**禁止**包含：条件判断业务规则、数据库查询、金额计算、状态变更逻辑。
- 所有请求体与响应体必须通过 **Pydantic Schema（DTO）** 定义，严禁直接传递 ORM 模型或领域实体。

**违反示例**：

```python
# ❌ 严禁：业务规则写在 router 中
@router.post("/borrow")
def borrow(req: BorrowRequest, db: Session = Depends(get_db)):
    card = db.query(BorrowCard).filter_by(card_no=req.card_no).first()
    if not card or card.status != "ACTIVE":          # 业务规则！
        raise HTTPException(400, "借阅证无效")
    loans = db.query(Loan).filter_by(reader_id=card.reader_id).all()
    if len(loans) >= 5:                              # 硬编码规则！
        raise HTTPException(400, "超出借阅数量")
```

```python
# ✅ 正确：router 只做转发
@router.post("/borrow")
def borrow(req: BorrowBookRequest, svc: CirculationService = Depends(get_circulation_service)):
    return svc.borrow_book(req)
```

## 第七条 权限控制原则

**三类角色的权限必须严格区分，权限校验必须在服务端完成。**

- 角色枚举：`READER`（读者）、`LIBRARIAN`（图书管理员）、`ADMIN`（系统管理员）。
- 权限矩阵以 `specs/01-clarifying-questions.md` 的 **D-05** 为准。
- 权限校验**必须**在应用服务层或通过依赖注入的守卫完成，**不得**仅依赖前端隐藏按钮。
- 读者的数据访问必须校验**资源归属**：读者只能访问 `reader_id` 等于自身的数据，服务端不得信任请求参数中的 `reader_id`。
- 已软删除的记录（借阅证、图书标题、馆藏副本）**仅系统管理员可查**，其他角色查询结果中必须过滤。

**违反示例**：`GET /api/readers/{reader_id}/loans` 直接按路径参数返回数据，不校验当前登录读者是否为该 `reader_id`。

## 第八条 业务规则集中原则

**借阅数量、借阅期限、超期罚款、预约规则必须集中在领域层实现，不得散落。**

- 借阅规则 → `BorrowPolicyService` 或等价策略类
- 罚款规则 → `FineRuleService` 或等价策略类
- 预约规则 → `ReservationService`（领域服务）
- 规则数值**必须从数据库读取**（`borrow_policies` / `fine_rules` 表），**严禁**硬编码为代码常量。

**推荐设计模式使用位置**：

| 模式 | 使用位置 | 用途 |
|---|---|---|
| **Strategy** | 借阅规则、罚款规则 | 不同读者类型 / 不同借出物类型的差异化规则 |
| **Repository** | 基础设施层 | 持久化领域对象，隔离 ORM |
| **Service Layer** | 应用服务层 | 组织用例流程，控制事务 |
| **DTO** | 表现层与领域层之间 | 隔离接口契约与领域模型 |
| **Factory** | 领域层 | 创建不同类型的读者或馆藏资源 |
| **MVC** | 表现层 | 分离路由、服务与模型 |

**违反示例**：在 `BorrowPolicyService` 中写 `if reader_type == "UNDERGRADUATE": max_count = 5`。

## 第九条 数据一致性与事务原则

**涉及多表变更的操作必须在单个事务内完成。**

必须使用事务的操作及其范围（详见 `specs/01-clarifying-questions.md` 的 **D-46c**）：

| 操作 | 事务范围 |
|---|---|
| 办理借书 | 校验额度 → 创建 Loan → 更新 LibraryItem 状态 |
| 办理还书 | 更新 Loan → 更新 LibraryItem → 生成 FineRecord → 处理预约预留 |
| 预约图书 | 校验队列 → 创建 Reservation |
| 办理借阅证 | 校验读者 → 生成证号 → 创建 BorrowCard |
| 续借 | 校验次数 → 更新 due_at → 递增续借次数 |

- 事务边界由**应用服务层**控制，不得在 Router 中开启事务。
- 任一步失败必须整体回滚，严禁出现"部分成功"的中间状态。

## 第十条 测试闭环原则

**核心用例必须有自动化测试，测试必须先于或同步于实现完成。**

必须覆盖的场景（不少于实验二文档要求的 14 项，本项目扩展至 24 项，详见 `specs/15-test-plan.md`）：

| 类别 | 场景 |
|---|---|
| 借书 | 成功 / 借阅证无效 / 超数量 / 有超期未还 / 有未缴罚款 / 图书不可借 |
| 还书 | 成功 / 非本馆藏书 / 未找到借阅记录 / 超期生成罚款 |
| 预约 | 成功 / 重复预约 / 队列已满 / 无可借副本才可预约 / 队列顺序 / 取消 |
| 查询 | 读者查自己 / 馆员查任意读者 / 读者查他人失败 |
| 规则 | 不同读者类型额度差异 / 不同借出物类型罚款差异 / 宽限期边界 / 封顶边界 |
| 权限 | 普通读者执行管理员操作失败 / 馆员执行管理员操作失败 |
| 认证 | 登录成功 / 密码错误 / Token 过期 |
| 软删除 | 已删除记录读者不可见 / 系统管理员可见 |

- 测试分为**单元测试**（策略、计算逻辑）与**集成测试**（API 端到端）。
- 实现完成后**必须运行测试**；测试未通过不得提交。
- 测试失败时，Agent 须**先解释失败原因**，再做最小修复，不得注释掉失败测试。

## 第十一条 Git 审查原则

**Agent 修改代码后，人类必须审查 `git diff`，再决定是否提交。**

- Agent 每次完成任务后须报告：修改了哪些文件、为什么修改。
- 人类执行 `git diff` 查看实际变更内容。
- 提交前确认：无多余文件、无调试代码、无敏感信息、未修改 `specs/`（除非本任务就是文档任务）。
- Agent **不得**在未获授权的情况下执行 `git commit`。
- 若 Agent 修改了不该修改的文件，人类可执行 `git checkout -- <file>` 撤销。

**提交信息格式**：**英文标头 + 中文描述**。

```
<type>: <英文简短描述>

<中文详细说明>
```

`type` 取值：`docs` / `feat` / `fix` / `test` / `refactor` / `chore`。

## 第十三条 规格文档语言与命名原则

- 规格文档使用**中文**书写。
- 代码标识符使用**英文**（类名、函数名、变量名、表名、字段名、枚举值）。
- 文档中引用代码标识符时，使用反引号包裹，如 `BorrowPolicy`。
- 数据库表名使用**复数小写下划线**风格，如 `borrow_cards`。
- 枚举值使用**大写下划线**风格，如 `CHINESE_BOOK`、`BORROWED`。

---

## 第十四条 时间处理原则

**存储用 UTC，显示用北京时间。**

- 数据库统一存储 UTC 时间戳。
- API 传输使用 ISO 8601 格式并带时区标识，如 `2026-09-19T06:44:25Z`。
- 前端负责转换为北京时间（UTC+8）显示。
- **严禁**在数据库中存储不带时区标识的本地时间字符串。
- 服务端内部计算全部以 UTC 进行，严禁混用本地时间与 UTC。

---

## 第十五条 数据保留原则

**所有删除均为软删除，历史记录永久保留。**

- 借阅证注销 → 状态置为 `CANCELLED`，记录保留。
- 图书标题 / 馆藏副本删除 → `is_deleted = true`，记录保留。
- 借阅记录、罚款记录**永久保留**，不自动清理。
- 已软删除的记录**仅系统管理员可查**。

---

## 第十六条 范围控制原则

**不得实现 `specs/00-project-brief.md` 第 8 节明确列出的"暂不实现"功能。**

暂不实现清单：

- 支付系统真实扣款
- 图书条码扫描硬件
- 复杂全文检索
- 多校区馆藏调拨
- 微信或统一身份认证登录
- 高并发、分布式部署
- 生产级安全加固

同时，Agent **不得**自行扩张需求范围。若认为有必要新增功能，须先提出，由人类裁定。
